ROADMAP — nothing below is built yet

Pipeline Roadmap

Two concrete next steps for PianoBot5000's melody/chord pipeline, an open question for a new, separate interface piece, and the longer-term idea it's all in service of. Nothing below is built — the two pipeline steps are designed to plug into the existing code without adding a new model or stage; the interface piece is a genuinely different part of the codebase, not yet scoped.

STEP 1

Swing-aware quantization

Melody cleanup currently snaps every note onto a straight, evenly-subdivided beat grid (melody.py's _beat_grid). That's fine for most pop/vocal material, but it flattens anything with a pronounced swing feel, where the off-beat note lands closer to two-thirds of the way through the beat than exactly halfway.

Why per-section, not one global ratio?

Swing can vary within a single song — a swung bridge over an otherwise straight verse, say. Section boundaries already exist from structure.py's A/B/C labeling, so this reuses data the pipeline already computes instead of adding a new dependency.

Why filter to [0.25, 0.85] and take the median?

Onsets near either beat say nothing about swing — they're just on-beat notes. Restricting to the middle of the interval isolates the "and" notes. The median (not the mean) keeps a couple of mis-transcribed outliers from skewing the estimate.

Why fall back to 0.5?

A sparse section — mostly on-beat notes, or just a short one — won't have enough off-beat onsets to trust. Rather than let 2–3 noisy samples dictate the grid, sections under the sample threshold just stay straight.

What this deliberately doesn't cover

16th-note-level swing is a separate, smaller effect. The first version would only bend the primary 8th-note split point and leave 16ths evenly spaced within each swung half, rather than modeling swing at two subdivision levels simultaneously.

STEP 2

Learn the sections, not the song

Today, sections are cosmetic — melody and chords are derived once, continuously, across the whole song, oblivious to section boundaries (see pipeline.py: sections only ever reaches assemble_midi(), for text markers). So two occurrences of the same section — two verses that are musically identical — can come out sounding different, purely from independent transcription noise. The idea: arrive at solid, repeatable A/B/C sections by learning each section once and reusing that one learned version everywhere it recurs, instead of re-deriving it fresh, inconsistently, every time.

Why consolidate at all?

Right now two musically identical sections can come out of the pipeline sounding different, purely from independent transcription noise between occurrences. Consolidating fixes that by settling on one agreed-upon version per section label, instead of trusting whichever version the model happened to produce at each timestamp.

The confidence signal is half-built already

ChordEvent already has a confidence field (types.py), but chords.py's extract_chords() never actually populates it from Chordino's output — that's a prerequisite here. Basic Pitch's amplitude (already used for note velocity) is the closest existing proxy on the melody side.

Cross-occurrence agreement, not just per-note confidence

Beyond each model's own confidence, compare occurrences against each other: how many of A's real occurrences in the song agree on a given slot's note or chord. Independent agreement across separately transcribed occurrences is itself evidence something is real music, not noise.

What "revert to" means

When occurrences disagree, there needs to be a deterministic rule for which one wins — "highest-confidence occurrence takes it all" vs. "per-slot majority vote." Worth deciding from real disagreement patterns on an actual song, not settled in the abstract here.

INTERFACE

Playback via Neothesia

A different kind of next step from the two above — not a change to how melody/chords/structure get analyzed, but a new, separate part of the codebase: something to actually watch and hear a generated arrangement, instead of just opening the .mid file in whatever happens to be installed. The plan is to lean on Neothesia, an existing open-source falling-notes MIDI visualizer, rather than building a visualizer from scratch. First iteration: just get a generated .mid file playing in it.

What we verified

Neothesia is a standalone native Rust app (GPL-3.0) — not a Python dependency, installed separately (Flathub, the AUR, a GitHub release binary, or cargo build). Its own source shows Song::from_env() reading std::env::args()[1] as a MIDI file path to auto-load on launch — so neothesia song.mid opens straight into playback, no in-app file picker needed. It also needs a .sf2 soundfont configured once through its own settings UI, outside PianoBot5000's control. A separate neothesia-cli crate exists too, but it's a headless MIDI→video exporter (via ffmpeg), not an interactive player — a possible bonus path later, not this.

What's still open

Deliberately undecided for now: whether launching it blocks the terminal until the window closes, or returns immediately; whether the neothesia binary is assumed to be on PATH or configurable; whether this becomes a pianobot play-style CLI command, its own small script, or just a documented manual step for the first cut; and whether it's worth a preflight "is Neothesia installed?" check like the existing model stages have.

LONGER VISION — CONTEXT ONLY, NOT PLANNED YET

Sections as reusable, drillable musical ideas

Once a section is consolidated into one solid, repeatable pattern, it stops being a one-off transcription of a single song and becomes a reusable building block: the same learned "A" could be transposed into other keys, or have new musical ideas layered onto it with increasing complexity — turning each learned section into a small, drillable exercise for exploring different melodic and harmonic options.

Nothing here is being built — it's the reason solid section consolidation (Step 2, above) matters beyond just cleaning up one song's MIDI file.

Neither step is built. Step 1 plugs into melody.py's clean_melody / _beat_grid. Step 2 plugs into assemble.py's assemble_midi, reusing Section groupings structure.py already produces. Neither adds a new pipeline stage, a new model, or a new CLI dependency.
